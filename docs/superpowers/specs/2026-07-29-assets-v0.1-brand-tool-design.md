# Arai Hû Assets v0.1.0 and Brand Tool Design

**Status:** Approved design

**Date:** 2026-07-29

## 1. Purpose

Turn the current identity exploration into the first intentional release of the
Arai Hû assets repository and the foundation of a reusable asset tool.

The first public tag is `v0.1.0`. It publishes the current brand system,
deterministic platform assets, a small licensed UI icon set, sprites, a
language-neutral catalog, and an engineering proof site. Version `v1.0.0`
remains reserved for a complete and stable icon-set contract.

This work also proves that Goshtoso can render a public brand site with the
visual quality of the existing identity proof, and establishes public brand and
license pages at `araihu.com`.

## 2. Product boundaries

The system has three repositories with separate responsibilities:

- `assets` owns canonical artwork, manifests, provenance, deterministic
  generation, release artifacts, `catalog.json`, and the engineering proof.
- `goshtoso` owns generic accessible sprite rendering, its default Heroicons
  integration, and the first client-side generator consuming `catalog.json`.
- `ahairu` owns the public multilingual `/brand/` and `/license/` experience at
  `araihu.com`.

The assets repository does not write into another repository. Consumers obtain
release artifacts or run an explicit export into a directory they control.

## 3. Release scope

### 3.1 Included in `v0.1.0`

- Canonical current Arai Hû product identity sources.
- Brand icon and horizontal-logo outputs.
- Transparent, supplied-plate, adaptive, light, dark, monochrome, grayscale,
  and designed tinted appearances where applicable.
- Optical UI framing and mask-safe launcher framing.
- Web, PWA, Android, and Apple platform exports.
- Individual brand SVGs and a brand sprite.
- A curated 20–30-icon Heroicons seed set.
- Individual normalized UI SVGs and a UI sprite.
- Third-party provenance, license notices, and checksums.
- Versioned, language-neutral `catalog.json`.
- Deterministic Go command-line tool and stable Make targets.
- Exhaustive engineering proof site generated from catalog data.
- Release archives containing distributable artifacts and notices.

### 3.2 Deferred beyond `v0.1.0`

- Claiming a complete or stable icon API.
- A public runtime Go asset library or embedded asset filesystem.
- Client-language code generation inside `araihu-assets`.
- Arai Hû-specific public bindings in Goshtoso.
- Wholesale vendoring of every Heroicon.
- A permanent `archive/` directory for old design concepts.

## 5. Namespaces and naming

Assets use two explicit icon namespaces:

- `icons/brand`: identity marks controlled by Arai Hû.
- `icons/ui`: permissively licensed interface icons.

The first UI source is:

```yaml
name: heroicons
alias: hi
version: v2.2.0
```

The manifest contains an explicit allowlist. A source entry such as
`16/solid/academic-cap.svg` generates:

```text
dist/icons/ui/heroicons/16-solid-academic-cap.svg
```

Its sprite symbol is:

```text
hi-16-solid-academic-cap
```

No manifest glob silently expands the public icon set. Mutable `master` URLs
are forbidden.

## 6. Brand output contract

Each supported product declares outputs along these dimensions:

- Artwork: icon or horizontal logo.
- Surface: transparent or supplied plate.
- Appearance: adaptive, light, dark, monochrome, grayscale, or designed tint.
- Framing: optical UI or mask-safe launcher.
- Format and platform target.

Generated platform outputs include:

- Web: SVG favicon; 16 and 32 pixel PNG favicons; touch icon; PWA `any` and
  `maskable` icons at 192 and 512 pixels.
- Android: adaptive foreground/background, API 33 monochrome layer, and legacy
  density exports.
- Apple: opaque 1024-pixel light, dark, and grayscale/tinted catalog images.
- General: individual SVGs, brand sprite, catalog entries, and checksums.

Variants are generated from canonical geometry and named recipes. They are not
independent hand-maintained copies. Circle, squircle, and other operating-system
masks are proof simulations unless a platform requires a concrete output.

Tinting has two meanings and must not be conflated:

- Designed brand tints are generated masters recorded in the catalog.
- Runtime CSS coloring is allowed only for assets classified as monochrome or
  tintable.

Protected multicolor artwork must not be converted to `currentColor` by a
consumer component.

## 7. Tool contract

The long-term tool is a Go CLI. Make provides the stable contributor interface.

Proposed CLI commands:

```text
araihu-assets vendor
araihu-assets build
araihu-assets verify
araihu-assets export --output <directory>
araihu-assets catalog
```

Stable Make targets:

```text
make vendor
make generate
make verify
make check
make proof
```

Behavior:

- `vendor` downloads only manifest-selected upstream files and verifies their
  provenance and hashes.
- `build` produces all declared individual assets, platform assets, sprites,
  catalog entries, notices, and checksums.
- `verify` checks source safety, geometry, naming, color behavior, provenance,
  raster requirements, sprites, catalog integrity, and reproducibility.
- `export` writes real files beneath a consumer-selected output directory.
- `catalog` validates and reports the generated catalog.
- `make check` regenerates in temporary output and rejects drift.

The module may be installed with Go's tool dependency mechanism, but Go is a
producer convenience rather than the interoperability contract. Release
archives and `catalog.json` remain first-class outputs.

## 8. Catalog contract

`catalog.json` is the canonical language-neutral consumer contract. It describes
generated release artifacts only; canonical working sources that are not
distributed do not become catalog entries.

Entries include enough information for filtering, rendering, documentation,
verification, and client-owned binding generation. Core fields include:

```text
schemaVersion
canonicalName
namespace
product
artwork
appearance
surface
framing
format
dimensions
spriteSymbol
colorBehavior
license
source
checksum
identityRevision
```

The assets CLI does not generate Go source in `v0.1.0`. Goshtoso introduces the
first catalog consumer and binding generator. It generates typed names for its
default Heroicons support and can be invoked by Arai Hû projects to generate
project-local brand bindings. Arai Hû-specific names do not enter Goshtoso's
public package.

## 9. Goshtoso integration

Goshtoso remains brand-neutral. It owns a generic sprite component that handles:

- asset or sprite URL;
- symbol name;
- size;
- accessible label;
- decorative state;
- CSS classes;
- inline or external sprite mode;
- `currentColor` behavior for compatible UI icons.

Goshtoso also ships default typed Heroicons support and a compatible default
sprite. Asset geometry, optical framing, brand colors, designed tinted masters,
platform padding, raster sizes, licenses, provenance, and checksums remain the
assets repository's responsibility.

## 10. Proof site and public site

The engineering proof and public brand site are related but distinct products.

### 10.1 Engineering proof

The assets repository generates an exhaustive inspection surface covering:

- plausible web and mobile sizes;
- light, dark, transparent, supplied, and tinted surfaces;
- optical and launcher framing;
- operating-system mask simulations;
- platform output comparisons;
- individual and sprite rendering;
- minimum-size and visual-weight checks.

It is driven from catalog and scenario data and produces reference screenshots.
The Impeccable review skill is used as a visual-quality gate.

### 10.2 Public brand site

The `ahairu` repository publishes a curated Goshtoso-built experience:

- `/brand/`: canonical English brand guidance and downloads.
- `/license/`: authoritative English terms.
- `/pt-br/brand/` and `/es/brand/`: localized brand guidance.
- `/pt-br/license/` and `/es/license/`: clearly informational translations.
- `/en/brand/` and `/en/license/`: redirects to canonical English routes.

The public brand page covers the identity, approved variants, sizing, clear
space, incorrect use, web/mobile examples, downloads, developer integration,
attribution, and a prominent link to the license.

The license separates Arai Hû brand terms from third-party UI icon licenses.
Unmodified brand assets may be redistributed within integrations and
documentation with attribution, preserved notices, and no implied endorsement.
Modified marks, standalone redistribution, merchandise, another identity, or
other endorsement-sensitive uses require permission. Heroicons remains governed
by its upstream MIT license.

## 11. Public metadata contract

Every public page generates:

- unique localized title and description;
- absolute canonical URL;
- Open Graph title, description, locale, URL, and bespoke image;
- X/Twitter card metadata;
- reciprocal `hreflang`, including `x-default`;
- language and content type;
- appropriate `theme-color`;
- favicon, Apple touch icon, and web-app manifest links;
- robots directives and sitemap entry;
- appropriate structured data.

`/brand/` uses `Organization` and `Brand` structured data. `/license/` uses
`WebPage` data with visible version and effective-date information. Metadata
validation is a build gate. Generic descriptions, relative canonicals, and
starter preview images are forbidden.

A bespoke social-preview image is generated once during implementation after
copy and visual direction stabilize, then inspected before use.

## 12. Visual parity evaluation

Migrating the public experience to Goshtoso is an explicit component-system
evaluation. Acceptance requires:

- equivalent hierarchy and visual confidence;
- readable dense asset comparisons;
- correct light, dark, transparent, and tinted presentation;
- purposeful mobile layouts;
- stable layout while variants change;
- keyboard and reduced-motion support;
- no bespoke JavaScript where a reusable component should own behavior.

Page-specific CSS is allowed for brand art direction. Structural shortcomings
must be recorded as Goshtoso issues rather than hidden with fragile page hacks.

## 13. Reproducibility and supply-chain safety

The repository builds offline after dependencies are vendored.

- Upstreams use immutable releases and recorded commits.
- Selected vendored sources and generated `dist/` artifacts are tracked.
- The catalog has an explicit schema version.
- Ordering, formatting, and timestamps are deterministic.
- Raster renderer and settings are pinned.
- Release archives include assets, catalog, checksums, notices, and licenses.
- A clean rebuild must be byte-identical to tracked output.

Vendor URLs are constructed only from validated manifest fields. The tool
rejects unexpected hosts, absolute paths, and traversal components. Downloads
have timeouts and size limits. Hashes are checked before replacement.

Exports are confined beneath the requested output directory. They never delete
unrelated files. A collision fails unless the existing file is byte-identical.
Temporary output is fully built and validated before publication.

## 14. SVG validation

Every distributed SVG must have:

- a valid expected `viewBox`;
- no script, event attributes, executable content, external URLs, remote fonts,
  or linked resources;
- no embedded raster content unless explicitly permitted;
- no duplicate or unstable IDs;
- no editor metadata;
- predictable fill and stroke behavior;
- declared color classification;
- valid optical bounds and safe zones.

Sprite symbols cannot contain document-level elements. Normalization may remove
noise, but must not silently rewrite paths merely to reduce bytes.

## 15. Failure behavior

Commands fail without partially publishing output. Diagnostics identify the
manifest entry, source file, rule, expected value, observed value, and a
deterministic correction when one exists.

Warnings are limited to non-release concerns. Geometry, licensing, provenance,
accessibility, catalog consistency, and reproducibility violations are errors.

Representative failures:

```text
manifest: unknown source alias "hero"
vendor: checksum mismatch for 16/solid/check.svg
build: protected multicolor asset cannot use currentColor
verify: apple icon must be opaque
export: destination escapes output root
check: dist/icons/ui/sprite.svg differs from generated output
```

## 16. Tests and release gates

Testing combines:

- Go unit tests for manifests, transforms, naming, export confinement, and
  catalog validation;
- golden tests for normalized SVGs, sprites, and catalog output;
- deterministic rebuild tests;
- SVG safety and geometry validation;
- raster size, opacity, and safe-zone checks;
- proof-site interaction, accessibility, responsive, and screenshot checks;
- Goshtoso component and generated-binding tests;
- static-site HTML, metadata, sitemap, localization, and link validation.

The assets `v0.1.0` tag requires:

- an intentional release tree without historical numbered public paths;
- deterministic generation of every declared artifact;
- passing brand geometry and platform checks;
- complete Heroicons provenance, MIT notice, and checksums;
- sprites resolving every catalog symbol;
- valid catalog schema and entries;
- byte-identical offline rebuild;
- passing functional, accessibility, and visual proof review;
- release archive matching tag contents;
- README documentation for installation, export, catalog use, and licensing;
- no mutable upstream or public `v11` paths.

Compatibility is additionally proven by Goshtoso consuming the catalog and by
`araihu.com` building the localized public pages with released artifacts. Their
deployment does not have to be atomic with the assets tag.

## 17. Control-plane execution

Implementation begins only after this specification and its implementation plan
are approved. A persistent control-plane ledger coordinates isolated worktrees
across the three repositories.

Each workstream records:

```text
repository
worktree
branch
owner
inputs
outputs
dependencies
acceptance tests
current commit
review state
integration state
```

The workstreams are:

1. Reconcile the current assets baseline and release tree.
2. Implement the asset CLI and manifests.
3. Normalize brand sources and generate variants.
4. Vendor the Heroicons seed and generate UI artifacts.
5. Assemble and validate the catalog and release.
6. Build the engineering proof.
7. Add Goshtoso sprite support and catalog consumption.
8. Build the public `araihu.com` brand and license pages.
9. Run cross-repository release verification.

Shared contracts land before dependent work begins. Workstream owners do not
edit files owned by other workstreams. Integration is explicit, reviewed, and
recorded in the ledger.
