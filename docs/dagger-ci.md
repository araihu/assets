# Dagger CI

All project CI logic lives in the Dagger module pinned to Engine `v0.21.8`.
GitHub Actions keeps provider-only concerns: events, permissions, runner trust,
GitHub App tokens, artifact upload metadata, and reusable-workflow wiring.
The TypeScript SDK under `.dagger/sdk` is generated by Dagger v0.21.8 at
runtime, is ignored, and must never be replaced by a hand-written or versioned
fixture.

## Local validation

Install Dagger `0.21.8`, then run the same safe gates used by CI:

```sh
mkdir -p .dagger-inputs
printf '%s\n' '{"cache_namespace":"pr","run_nonce":"local"}' > .dagger-inputs/ci.json
dagger call ci --source=. --payload=.dagger-inputs/ci.json

printf '%s\n' '{"refresh_nonce":"local"}' > .dagger-inputs/acquisition.json
dagger call acquisition --source=. --payload=.dagger-inputs/acquisition.json
```

Acquisition may contact only the locked Muamba inputs. The CI function keeps Go
module network access disabled. Every run mounts named Dagger cache volumes only
for dependencies, build output, and tools. Pull requests use stable namespace
`pr`; protected push, manual, scheduled, tag, and reusable-workflow runs use
namespace `trusted`.

The Dagger runtime uses the digest-pinned Go 1.27.0 Debian trixie image. Its
librsvg bootstrap rejects any distro Cairo other than exact `1.18.4` and also
checks librsvg's `>=1.18.0` floor before configuration. Meson, Rust, cargo-c,
and librsvg remain independently versioned and digest-verified.

Cache namespace is an efficiency hint, not a security boundary. Dependabot pull
requests run on `ubuntu-24.04`; other pull requests use `hostinger-vps-pr`, and
protected runs use `hostinger-vps-trusted`. Runner admission,
isolated Engine socket/data, and host ACLs prevent PR workloads from reaching
trusted cache storage even if PR-owned code requests another cache name. Workflow arguments
must never be treated as authorization. PR cache rollout remains gated on that
host isolation.

The runner needs only Bash and the exact Dagger CLI. CI first runs
`scripts/dagger/preflight-audit.sh`, a Dagger Core container call that mounts
`.dagger` and runs the locked npm audit inside pinned
`node:22.14.0-bookworm-slim@sha256:1c18d9ab3af4585870b92e4dbc5cac5a0dc77dd13df1a5905cea89fc720eb05b`; it does not load this TypeScript module. The
project `dagger call ci` starts only after that preflight succeeds. The CI
container repeats the audit as defense in depth.

Inside the Dagger runtime, `scripts/check-ci-workflow.sh` requires Git, grep,
and Ruby. Git remains mandatory even when the mounted source deliberately omits
`.git`; tracked generated-SDK checks activate only when Git metadata is present.

## External reads and effects

Remote GitHub reads and every mutation are separate functions with function
cache disabled. They also require a fresh non-secret nonce so Dagger cannot
reuse an individual network or mutation exec layer. Tokens use Dagger `Secret`
arguments and environment secret providers:

```sh
dagger call release-fanout-plan \
  --source=. \
  --release=v0.2.4 --run-nonce=123-1 \
  --github-token=env://GITHUB_TOKEN \
  export --path=.dagger-out/fanout
```

Fan-out uses the Go `cmd/releasefanout` tool in the existing
`github.com/araihu/assets` module. Dagger compiles it with the pinned Go image;
the exported binary is static so the Actions runner needs no matching libc.
Planning and dispatch mount token files only after compilation. No shell or Ruby
scripts implement the fan-out. Actions passes quoted arguments to Dagger, then
uses the exported Go binary to append the verified repository selection to its
output file. The repository is fixed to `araihu/assets` in the Go implementation.

The `plan` command verifies the published tag, release.json, archive hashes, and
tag stability before writing `plan.json`. `dispatch` validates that plan against
the current enrollment manifest before sending the six-field release envelope.
It attempts every enrolled consumer, aggregates failures, and replays all
consumers on an explicit retry. A successful dispatch means GitHub accepted the
event, not that a downstream workflow finished or merged a change.

Local checks are `go test ./internal/releasefanout ./cmd/releasefanout` and
`go vet ./internal/releasefanout ./cmd/releasefanout`. The CLI accepts flags and
mounted token files; it does not parse environment variables or log credentials.

Publication and dispatch functions cause external writes. Run them only with an
explicit operator-approved `effect-nonce`. Local safe validation does not need
GitHub credentials and does not publish, dispatch, upload, tag, or release.
